Four players, four clients: three on their own computers, and the fourth on the server computer, which also plays. The server secretly picks one imposter; the other three are crewmates. The imposter kills crewmates who are close, once every 10 seconds. Anyone can call one meeting to vote someone out. Crew wins by voting the imposter out; the imposter wins at one against one. Browsers can't open raw sockets, so a small local Node agent does it.

The game rules never mention net or dgram. Clients ask; the server decides.

The game runs in a browser tab, and a browser can't open raw TCP or UDP sockets. So each computer runs a small Node program, the local agent, which owns the real socket. The tab talks to it inside the same computer, so between computers there is only our own TCP or UDP. On the server, the TCP file and the UDP file offer the same four functions: connect, message, disconnect, send. The game rules only use those four, so changing protocol means swapping one file. And the server decides everything: a client only asks, for example "I want to kill", and the server checks it.

Head-of-line blocking

One lost packet blocks every newer position behind it.

TCP must deliver the old position first, even if it's already outdated. L toggles loss.

In TCP, the server listens on port 5000 and gets one socket per player. The operating system does the hard work: handshake, numbering, acknowledgements, resending, ordering. Our code never sees a lost packet. Four things were still our job. One: TCP is a stream of bytes, so one read can hold half a message; we send one message per line. Two: TCP waits to group small messages; we turn that off. Three: a pulled cable sends nothing, so we added a heartbeat: 5 seconds of silence means the player is gone. Four: a dead connection can't be reused, so the client opens a new one. The price of reliability: one lost packet blocks every newer position behind it. That's head-of-line blocking.

4 · The UDP version

UDP: nothing is promised. So we built it.

Server: one socket on :5001 for everyone. A player = an address that said HELLO, plus a secret token.

No connection. No delivery guarantee. No order. No goodbye.

1Handshake + token

{"t":"HELLO"}{"t":"WELCOME","tok":"9f2c…"}

Say HELLO until the server answers. The token proves who you are.

2Seq + ACK

{"t":"MSG","seq":7,"type":…}{"t":"ACK","seq":7}

Each important message gets a number. The receiver confirms it.

3Retransmit

wait = 2 × round trip · 100–1000 ms

No confirmation in time? Send it again.

4Dedupe

seen it already → confirm, ignore

A message is never used twice.

5Order

seq 8 waits for seq 7

Early messages wait for the missing one.

6Give up

25 resends (≈ 2.6 s) or 5 s of silence

Then the player is considered gone.

Reliable lane MSG

login · join · start · kill · vote · end

{"t":"MSG","seq":7,"type":"player:kill",…}

Must arrive, once, in order.

Fast lane FAST

positions only · 20 per second

{"t":"FAST","n":345,"type":"player:move",…}

Never resent. An old position is just dropped.

Same loss on both. TCP freezes; UDP shows the next position 50 ms later. L toggles loss.

UDP promises nothing: packets can be lost, duplicated or arrive out of order, and nobody tells you when a player is gone. The server has one socket for everyone, so we built sessions: the client says HELLO, the server answers WELCOME with a secret token, and every later packet carries it. Then we rebuilt reliability ourselves. Each important message gets a number and must be confirmed. No confirmation in time: we send it again, and the waiting time adapts to the network. Duplicates are ignored, and early messages wait for the missing one. After 25 resends, or 5 seconds of silence, the player is gone. Positions skip all of this on purpose: 20 per second, never resent. With the same loss, TCP freezes, while UDP simply shows the next position 50 milliseconds later.

TCP sees a crash at once. A pulled cable: both need our heartbeat.

What you just saw, explained. Four players at once. TCP gives each player their own socket. UDP has one socket for everyone and tells players apart by address and token. Sending to a room means one send per player, in both. Node handles one event at a time, so two actions at the same instant never collide. And the server knows who you are from your session, never from what your message claims. Now disconnections, where the protocols really differ. If a game crashes, TCP knows at once, because the operating system closes the connection. UDP has no connection, so only 5 seconds of silence reveal it. If a cable is pulled, nobody sends anything, so both need our heartbeat. Then the same code runs in both: the player is removed, the others are told, a new host is picked, and the game ends if a side has won.

7 · Edge cases & inconsistencies

What could break, and why it doesn't

Game rules

  • Roles are sent privately: nobody else learns who the imposter is.
  • The server checks every kill: role, 10 s cooldown, distance.
  • Too-fast or off-map moves are corrected.

Players leaving

  • Host leaves → a new host is picked.
  • Imposter leaves → the crew wins.
  • Bad or unknown messages are ignored. The server never crashes.

Known limits

  • A reconnecting player can't rejoin a running game.
  • Restarting the server ends all games.
  • UDP may drop a player after a short Wi-Fi hiccup (≈ 2.6 s).

The server checks every rule, so one bad client can't break the game.

The project we started from trusted the players completely: our first test found 16 bugs, like the imposter's name visible to everyone. Now the server checks every rule itself. Roles are sent privately. Every kill is checked: role, cooldown, distance. Impossible moves are corrected. When a player leaves, the game adapts: new host, or a crew win if the imposter left. Broken messages are ignored, so the server never crashes. What's not perfect yet: a reconnecting player can't rejoin a running game, a server restart ends all games, and in UDP a short Wi-Fi hiccup can drop a player a bit early.

TCP

Advantages

  • Reliable and ordered for free
  • Crash seen at once
  • Less code

Drawbacks

  • We must split messages
  • One loss blocks everything after it
  • Needs a heartbeat for pulled cables

UDP

Advantages

  • One message = one packet
  • Reliable only where needed
  • No freeze on lost positions

Drawbacks

  • We built sessions, confirmations, order
  • Crash seen only by silence
  • Bigger messages

TCP is best for

login, rooms, kills, votes, scores: things that must arrive.

UDP is best for

movement: a lost position costs 50 ms, not a freeze.

Reliable for events. Unreliable for state that expires.

We measured both versions. A crash: TCP sees it at once, UDP after 5 seconds. With 20 percent of packets dropped, the UDP game still finished and passed all 38 checks; about 40 percent of positions were lost, as the theory predicts, but the game stayed playable because a new position comes every 50 milliseconds. In TCP, the operating system repairs the loss, so movement stalls instead. UDP costs more: bigger messages and about 60 percent more code. Our verdict: TCP for everything that must arrive. UDP for movement. Reliable for events, unreliable for state that expires.

9 · Challenges & optimizations

What broke, and how we fixed it

Libraries hid the sockets

Socket.IO and Express: TCP hidden underneath.

Removed. Only net and dgram.

The browser

Web pages can't open raw sockets.

A local Node agent does it.

Trusting players

Players could cheat. 16 bugs found.

The server checks everything.

Too many messages

Up to 144 positions per second.

20 per second, 2 when standing still.

Silent players

A dead player stayed "connected" forever.

Heartbeat: 5 s of silence = gone.

UDP promised nothing

Lost, duplicated, reordered packets.

Numbers, confirmations, resends, token.

Six problems, six fixes. The original project used libraries that hid TCP, so we removed them. Browsers can't open sockets, so a local agent does it. Players could cheat, so the server now checks everything. Positions were sent up to 144 times per second; now 20. Dead players stayed connected; now a heartbeat removes them. And UDP promised nothing, so we built reliability ourselves. Then the optimizations, each with a number. The hardest part was not writing sockets: it was discovering what the libraries had been doing for us.

Backup · network weaknesses we faced

Each protocol hurt us differently

TCP onlynet · the OS is reliable for us, but rigid

No message boundaries

One read can hold half a message, or two glued together.

Newline framing: one JSON object per line, safe for split UTF-8.

Nagle delays small writes

Small, frequent game messages wait to be batched.

setNoDelay(true): every message leaves at once.

Head-of-line blocking

One lost segment freezes every newer position behind it.

Cannot be removed, so we shrink it: 20 Hz instead of every frame, and the receiver glides.

A dead peer is silent

A pulled cable sends nothing; keep-alive needs about 2 hours.

PING / PONG every 1 s, 5 s timeout, reconnect every 2 s.

UDP onlydgram · fast and free, but nothing is guaranteed

Datagrams get lost

A kill or a vote may simply never arrive.

seq + ACK + resend; the timeout adapts: RTO = 2 × measured RTT.

Duplicates and reordering

The same event twice, or seq 8 before seq 7.

Dedupe by seq, and a buffer that delivers in order.

No connection, no goodbye

Who is this packet from? Is the other side still there?

HELLO → WELCOME sessions by ip:port + token, BYE, 5 s heartbeat.

Resends can make it worse

Hammering a stalled network; big datagrams get fragmented.

RTO floor of 100 ms, positions never resent, datagrams under 1200 bytes.

Backup slide for questions: the network weaknesses of each protocol and what we did about each one. TCP: no message boundaries, Nagle's delay, head-of-line blocking, and silent dead peers. UDP: lost datagrams, duplicates and reordering, no connection and no goodbye, and the risk of making a bad network worse with resends or oversized datagrams.

Bonus: playing across different networks. Tailscale is a VPN that puts the four laptops on one private network, and the server already listens on every network, so no code changed. We played a full game on the TCP version with one player on 4G and captured it. The 4G network blocked a direct connection, so Tailscale relayed the traffic through its server in Amsterdam. The round trip went from about 10 milliseconds on the LAN to about 120, and the game stayed fully playable: no segment lost, no reset, and a single retransmission that turned out to be useless, because only the acknowledgement was late. One caution for UDP: Tailscale's relay carries traffic over TCP, so through a relay our UDP would really travel inside TCP. Here is the capture, taken inside the tunnel so our messages are readable. At the top, the first kill: the player keeps sending moves, and packet 1176 is the server's player:killed, 132 bytes, acknowledged 41 milliseconds later. Further down, the only retransmission of the whole game: the server sent a PONG, the player acknowledged it, but the acknowledgement was still crossing the relay when the server's timer fired, so the server sent the PONG again. Wireshark marks it spurious, and the player answers with a duplicate ACK whose SACK block says: I already have those bytes. Below, Follow TCP Stream shows our protocol as it really travels: one JSON message per line, the player in red, the server in blue. To close: TCP gives you a promise, and you pay with freezes.
