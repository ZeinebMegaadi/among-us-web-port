1 · The game

Competitive by design

Rules

  • 3 players: 1 imposter, chosen secretly by the server, against 2 crewmates.
  • Imposter kills a crewmate who is close enough (≤ 100 px), at most once every 10 s.
  • Any living player can call one emergency meeting per game: 30 s to vote for a suspect, or skip.
  • Crew wins if the imposter is voted out (or leaves). Imposter wins by killing both crewmates.
  • Play again: same room, the imposter role rotates, scores keep adding up.

Every player has a personal score

Kill+1imposter Vote for the imposter+1each correct voter Crew wins+2every crewmate, alive or dead Imposter wins+3imposter

End screen: the winning side, then a ranking sorted by points.

Registration & login

Name + password. Password stored as a scrypt hash; the player id is issued by the server.

Lobby & rooms

Create a room with a code. The room list is pushed to every client on each change.

Join & leave

The other players are told at once: player:joined / player:left.

Start & end

Only the host starts. Roles are sent privately. The server decides when it ends.

Real-time actions

Positions 20 times per second, kills, meetings and votes, all checked by the server.

Scores & results

Points, ranking and winner, sent to every player in game:ended.

Disconnection

Detected (FIN / RST, BYE, 5 s heartbeat) and cleaned up. The others keep playing.

In both versions

All 7 features, same rules and same messages. Only the transport changes.

First, the game, because it decides what the network has to carry. Three players. The server secretly picks one of them as the imposter; the other two are crewmates. The imposter can kill a crewmate who is close enough, at most once every ten seconds. Any living player can call one emergency meeting per game, and everyone alive then votes for a suspect or skips. The crew wins if the imposter is voted out; the imposter wins by killing both crewmates. So it is competitive: every player has a personal score. A kill is worth one point, voting for the imposter one point, a crew victory two points to every crewmate, and an imposter victory three points. The end screen shows the winner and a ranking, and when you play again the imposter role rotates and the scores add up. Below, the seven features the project requires: registration and login, lobby and rooms, joining and leaving, game start and end, real-time actions, scores, and disconnection handling. All seven exist in both versions, with the same rules and the same messages.

The game rules never mention net or dgram. Clients ask; the server decides.

Now the architecture. One server computer and three client computers. The game screen is a normal browser tab, and a web page is not allowed to open a raw TCP or UDP socket. So each client runs a small Node program next to the browser, the local agent, which owns the real socket. The tab talks to the agent over loopback, which never leaves the computer, so between computers there is only our own TCP or our own UDP traffic. A desktop Electron build exists too and works the same way. On the server, both transports offer exactly the same four operations: connect, message, disconnect and send. The game rules only use those four, so switching protocol means switching one file, chosen with --proto. That is how the two versions keep identical rules. And the server is authoritative: a client only asks, for example "I want to kill this player"; the server checks the role, the distance and the cooldown with its own data, and then tells everyone what happened.

Head-of-line blocking

In the TCP version the server opens one listening socket on port 5000. Every client that completes the three-way handshake gets its own dedicated socket, and that socket is the player's session. The first thing the server sends is a welcome message; only then does the client consider itself connected. The operating system does a lot for us: sequence numbers, acknowledgements, retransmission and in-order delivery all happen in the kernel, and our code never sees a lost packet. But four things were still our job. First, TCP is a stream of bytes, not of messages: one read can contain half a message, or two glued together, so we put exactly one JSON object per line. Second, Nagle's algorithm delays small writes to batch them, so we turn it off. Third, if a cable is pulled, nothing arrives to tell us, and TCP's keep-alive would take about two hours, so we added a one-second heartbeat with a five-second timeout. Fourth, a dead connection cannot be revived: the client opens a brand-new one every two seconds. And here is the price of reliability: every byte must arrive in order, so one lost position holds back all the newer ones behind it. That is head-of-line blocking.

UDP promises nothing: a datagram can be lost, duplicated or reordered, and nobody tells you when the other side is gone. The server has one single socket for all players, and a datagram only tells us the sender's IP and port, so we built sessions ourselves. The client sends HELLO every second until the server answers WELCOME with a session id and a random token; every later datagram must carry that token, so faking someone's address is not enough to play as them. Then reliability, in one file used by both sides. Every important message gets a sequence number and must be acknowledged. If the ACK does not come back within the retransmission timeout, we resend. That timeout adapts: twice the smoothed round-trip time, kept between 100 milliseconds and one second, and, like TCP, we only measure the round trip on messages sent once: that is Karn's rule. Duplicates are acknowledged again but never delivered twice, and early arrivals wait until the gap is filled. A peer is declared dead after 25 resends without an answer, which is about 2.6 seconds on a LAN, or after 5 seconds of silence, whichever comes first. In this animation the ACK is lost: the client resends, the server recognises the duplicate, acknowledges it again, and does not deliver it twice. And the deliberate choice: positions skip all of this. They travel on a fast lane, 20 per second, never resent. With the same loss on both lanes, TCP freezes player two's screen until the old position is recovered, while UDP simply shows the next one 50 milliseconds later.

TCP knows at once when the OS can tell it. For a silent failure, both need our heartbeat.

Let's look closer at what you just saw. Three players act at the same time. TCP gives the server one socket per player, and that connection is the session. UDP uses a single socket for everybody, and the server tells players apart by their address plus their token. Sending to a room is not magic in either case: three players means three separate sends. Node handles every client on one event loop, so if a kill and a vote arrive at the same instant, they are two events processed one after the other, and the second is checked against the new state. No locks, no race conditions. And the server always decides who you are from your session, never from what your message claims. Now, disconnections, where the protocols really differ. When a client process crashes, TCP knows immediately, because the operating system resets the connection. UDP has no connection, so only silence reveals it: five seconds, or about three seconds when messages are waiting for an acknowledgement. When a cable is pulled, nobody sends anything, so both versions rely on our heartbeat. Whatever the cause, the same game code runs: the player is removed, the others are told why, the host role moves on, an open meeting is closed if they were the last voter, and if the imposter left, the crew wins. Nothing crashes, and the disconnected client reconnects by itself.

7 · Edge cases & inconsistencies

What could break, and why it doesn't

Game rules

  • The imposter's identity is never in a public message; each role is sent privately.
  • A kill is checked on the server: role, both alive, no meeting, 10 s cooldown, distance from the server's positions.
  • A position outside the map is clamped; a move faster than walking speed is rejected and corrected, with a small tolerance for network jitter.
  • One meeting per player per game. Dead players cannot vote. Votes stay hidden until the end. A tie ejects nobody.
  • Joining is refused if the game started, the room is full or the name is taken; a taken color is swapped for a free one.

Sessions & network

  • The same account cannot play from two clients at once; a player id inside a message is ignored.
  • The leaver was the last voter → the meeting ends now. The host leaves → a new host is announced. The imposter leaves → crew wins.
  • Password check runs off the main thread; if the client vanished meanwhile, the reply is dropped.
  • UDP: a HELLO from a known address = the client restarted → fresh session. A wrong token → dropped, and it does not count as a heartbeat.
  • Bad JSON, unknown message types, an error in one handler: logged and ignored. The server never crashes.

Known limits

  • A reconnecting player goes back to the menu; they cannot resume a game in progress.
  • A player who leaves is removed from the final ranking, together with their score.
  • UDP: 25 resends take only ≈ 2.6 s on a LAN, so a short Wi-Fi hiccup can drop a player sooner than the 5 s heartbeat would. Next step: exponential backoff.
  • Our UDP layer does not split messages: one over 1200 bytes would rely on IP fragmentation (ours stay well below).
  • Rooms live in memory: restarting the server ends all games. Accounts are saved on disk.

Every rule is checked on the server, so one broken or malicious client cannot break the game for the others.

The project we started from trusted the clients completely. Our first test with three scripted clients found sixteen defects: the imposter's identity was in the public room list, a crewmate could kill, anyone could rename another player or end a meeting, and a position of x equals ninety-nine thousand was accepted. Today the server checks every rule with its own data. Roles are sent privately. A kill is checked for role, cooldown and distance, using the server's copy of the positions. A move that goes off the map or too fast is corrected, with a small tolerance so that normal network jitter does not punish honest players. Meetings, votes and room joins have their own rules. On the network side, we covered the awkward timings: the last voter leaving, the host leaving, the imposter leaving, a client restarting in UDP, a stale packet from an old session, or a client disconnecting while its password is being checked. And here is what we know is not perfect. A reconnecting player cannot resume a running game. A player who leaves disappears from the ranking. And in UDP, because the retry timer has no backoff yet, a short Wi-Fi hiccup can disconnect a player a little sooner than in TCP. We know why, and how we would fix it.

TCP

Advantages

  • Reliability and order done by the OS
  • Quit and crash seen at once (FIN / RST)
  • Less code to write and debug
  • Built-in flow and congestion control
  • Smaller messages in our design

Drawbacks

  • No message boundaries: we frame
  • Nagle delays small writes
  • Head-of-line blocking on positions
  • A dead peer is silent: needs a heartbeat
  • Reconnect = new handshake, new session

UDP

Advantages

  • One message = one datagram
  • Reliability chosen per message
  • No head-of-line blocking for positions
  • One socket for every player
  • We control every timer

Drawbacks

  • Sessions, ACKs, order, liveness: all ours
  • A crash is seen only through silence
  • No congestion control
  • Bigger messages: token, envelope, ACKs
  • Source address can be faked → token

TCP performed best at

login, lobby, rooms, kills, votes, scores: everything that must arrive.

UDP performed best at

movement under loss: a lost position costs 50 ms, not a freeze.

Reliable for events. Unreliable for state that expires.

We compared the two versions with metrics we chose ourselves. Detection: a crashed client is seen instantly in TCP, and after up to five seconds in UDP. Behaviour under loss: with 20 percent of the datagrams dropped on every side, the UDP version still finished a complete game and passed all 38 checks. Each client repaired its events with a handful of retransmissions, ignored around twenty duplicates and reordered about ten messages, while 37 to 41 percent of positions were simply lost, which matches the theory of two independent 20-percent losses. The game stayed playable because the next position always arrives 50 milliseconds later. In TCP we cannot drop bytes from inside a stream; the operating system repairs the loss, and the cost shows up as a stall instead. UDP also cost us: our messages are bigger, because each datagram carries the token, its own envelope and separate ACKs, and we wrote about 60 percent more transport code. Next, the advantages and drawbacks side by side. Our verdict: TCP is the better fit for everything that must arrive, with simpler code and instant crash detection. UDP wins for movement, because on a lossy network a lost position costs one frame instead of freezing everything behind it. Reliable for events, unreliable for state that expires.

9 · Challenges & optimizations

What broke, and how we fixed it

Libraries hid the sockets

Socket.IO + Express + fetch: all TCP underneath.

Removed all of it. Only Node net and dgram.

The browser sandbox

The game is a web page. Pages cannot open raw sockets.

A local Node agent owns the socket; the page talks to it over loopback.

Trusting the client

Player id in the payload; the imposter visible to everyone. 16 defects found.

Identity from the session. Roles private. The server validates every action.

Flooding the wire

A position on every rendered frame: 60 to 144 per second.

20 per second moving, 2 idle, no echo. Remote players glide.

Silent peers

"Connected" meant the socket opened. A silent peer stayed forever.

welcome + PING/PONG every 1 s, 5 s timeout, automatic reconnect.

UDP promised nothing

Datagrams lost, duplicated, reordered; source address can be faked.

seq + ACK + adaptive RTO + dedupe + order + session token.

These are the challenges we faced. The project we started from used Socket.IO, Express and fetch, so everything ran over HTTP and WebSocket: TCP underneath, with the sockets hidden. We removed all of it. A web page cannot open raw sockets, so a small local agent owns them. The old code trusted the player id written in each message and showed the imposter to everyone, so we bound identity to the session and made the server check every action. Positions were sent on every rendered frame, up to 144 times per second, so we limited them to 20. A silent peer used to stay connected forever, so we added a heartbeat. And UDP promised nothing, so we built sequence numbers, acknowledgements, an adaptive timeout, ordering and a session token. Then the optimizations, with their numbers: 20 positions per second instead of up to 144, and only 2 when standing still; no echo, which removes a third of the position traffic; smooth gliding between updates; a lobby list that is pushed instead of polled; no Nagle delay in TCP; an adaptive timeout and small datagrams in UDP; and password hashing that never pauses the game. The hardest part was not writing sockets: it was discovering what the libraries had been doing for us.
